## 목적

이 문서는 ClaFact 검증 실험실과 연결된 기능에서 발견된 문제, 그 증거, 원인, 조치, 미해결 과제를 한곳에 누적하는 공식 학습 원장이다. 운영 Claim·리뷰 큐·KOSIS 판정 이력과는 분리한다.

과거 항목은 Git 이력과 작업 대화에서 재구성했으므로 `Backfilled`로 표시한다. 미래 항목은 문제가 확인되는 즉시 추가하며, 해결 여부는 테스트 또는 재현 증거로 갱신한다. 추측은 사실처럼 기록하지 않는다.

## 상태 정의

- `Resolved`: 조치와 검증 증거가 있다.
- `Monitoring`: 조치는 했으나 실제 사용 데이터에서 관찰이 더 필요하다.
- `Open`: 재현되었지만 아직 해결하지 않았다.
- `Baseline`: 기존 문제이며 현재 변경의 회귀가 아님을 확인했다.

## 핵심 원칙

1. 업로드한 기사 본문 밖의 문장, 기사 추천·기자 프로필·구독 안내는 후보로 생성하지 않는다.
2. `후보 탐지`, `공식 근거 충분성`, `최종 사실 판정`은 서로 다른 단계다. 후보 미탐지로 근거 부족을 표현하지 않는다.
3. 모델 비교 결과에는 제공자·모델·실행 모드·호출 수·경과 시간·오류 여부를 함께 남긴다. API 키와 원문 외 민감 정보는 기록하지 않는다.
4. 모든 변경은 해당 문제 ID, 커밋, 테스트(또는 수동 재현 증거)를 연결한다.
5. **“실패의 기록은 프로젝트의 가치를 높인다.”** 성공과 실패를 모두 남기되, 특히 실패는 입력·실행 모드·증상·원인·보호 동작·후속 실험을 재현 가능하게 기록한다.

## 상세 기록

### VLAB-009 — HCX가 후보 문장 2번을 미탐지

- **증거:** 2026-07-26 화면 공유. 대상 문장에는 `2.6%`, `지난해 7월`, `15개월`, `가장 높은`이 포함된다.
- **영향:** 실제 검증할 수치·비교 주장이 후보군에서 빠져 재현율이 낮아진다.
- **현재 원인 가설:** 현재 HCX 프롬프트가 “공식 통계로 검증 가능한 수치 주장”을 한 번에 판단해, 후보 여부와 기사 안의 직접 공식 출처 인용 여부를 혼동한다.
- **확정 판단:** 후보 탐지 결과는 `탐지`가 맞다. 이 문장만으로 실제 수치의 참·거짓 또는 공식 근거 확보가 확정되는 것은 아니다.
- **해결:** HCX 프롬프트와 응답 계약을 `candidate`, `candidate_reason`, `evidence_status`, `evidence_reason`, `quoted_spans`로 분리했다. `needs_retrieval`은 후보 탈락이 아닌 정상 탐지 상태다.
- **검증:** `tests/test_detect_llm.py::test_judge_decision_keeps_comparative_numeric_claim_as_candidate`, `tests/test_experiment_lab.py::test_hcx_mode_preserves_candidate_and_evidence_status_separately`가 이 문장을 `candidate=true`, `needs_retrieval`로 고정한다.
- **후속 관찰:** 실 API HCX-005 응답의 JSON 준수율과 원문 인용 구간의 정확도는 골든셋 확장 시 계속 관찰한다.

### VLAB-010 — 제공자·모델이 드러나는 비교 체계

- **현재 확인:** 화면의 `HCX 실호출` 조건은 `CLAFACT_HCX_MODE=live` 및 `HCX_API_KEY` 설정이다. 이때 `HcxClient`가 CLOVA Studio의 HCX Chat Completions API를 호출하며, 기본 모델 값은 `HCX-005`다.
- **한계:** 현 화면만으로 각 호출의 HTTP 성공 상태, 모델 변경 여부, 요청 식별자, 원문 응답 파싱 실패를 충분히 감사할 수 없다.
- **목표 구조:** `provider=HCX`, `model=HCX-005`처럼 제공자와 모델을 결과 객체에 보관한다. GPT를 추가할 때는 동일 스키마의 `provider=OpenAI`, `model=<선택 모델>` 실행을 별도 열로 추가하며, HCX 결과를 덮어쓰지 않는다.
- **금지:** API 키, Authorization 헤더, 원문에 없는 문장을 로그나 화면 근거로 생성하지 않는다.

### VLAB-012 — 하이브리드의 성공과 구조적 한계

- **증거:** 2026-07-26 동일 기사 14문장 실행 화면 `20260726_114052.png`, `20260726_114004.png`, `20260726_114223.png`. Python 단독은 `13/14`, HCX 단독은 `11/14`, 하이브리드는 `13/14`였다.
- **성공 1 — 의미 판정 보강:** 2번 문장은 Python이 수치·비교 규칙으로 후보를 잡고, 하이브리드의 HCX가 `탐지`와 `검색 필요`를 분리했다. 이는 규칙 탐지 뒤에 의미 해석과 근거 상태를 붙이는 하이브리드의 실질 가치다.
- **성공 2 — 장애 내성:** HCX JSON 응답이 없거나 파싱에 실패한 문장에서도 하이브리드는 Python 후보를 보수적으로 유지했다. HCX 단독의 일시적 실패가 전체 재현율 하락으로 번지는 것을 막았다.
- **실패/한계:** 현재 하이브리드는 Python 후보 문장에만 HCX를 호출하는 직렬 게이트다. 따라서 Python이 놓친 문장은 HCX가 판별할 기회 자체가 없으며, `Python=false, HCX=true` 사례를 현재 하이브리드 실행으로는 발견할 수 없다.
- **해석:** 현재 구현은 `상호 보완형 결합`이 아니라 `Python 재현율 + HCX 의미 보강/오류 안전망`이다. 하이브리드가 Python보다 더 높은 재현율을 내는 설계는 아직 아니다.
- **후속 실험:** 검증 실험실에서는 모든 문장을 Python과 HCX에 독립 실행해 다음 다섯 유형을 집계한다.
  1. `P+ / H+`: 양쪽 모두 탐지
  2. `P+ / H-`: Python만 탐지(HCX는 정상 응답)
  3. `P- / H+`: HCX만 탐지 — 하이브리드 확장의 핵심 학습 자산
  4. `P- / H-`: 양쪽 모두 미탐지(HCX는 정상 응답)
  5. `HCX_ERROR`: HCX 실행·응답·파싱 실패 — 의미적 H-와 분리
- **구현:** 전체 비교에서 모든 문장을 Python과 HCX에 독립 입력하고 `P+/H+`, `P+/H-`, `P-/H+`, `P-/H-`, `HCX_ERROR`로 상호 배타 분류한다. 결과는 운영 DB와 분리된 연구 SQLite에 명시적으로 저장하며, CSV 내보내기와 `P+/H-`·`P-/H+` 사람 승인 골든셋 승격을 제공한다.
- **평가 계약:** `true_candidate`, `false_positive`로 사람 검토가 끝난 행만 정답 표본이다. `hold`와 미검토 행은 정밀도·재현율에서 제외한다. HCX 오류 행은 HCX 분류 지표에서 제외하고 HCX 평가 건수를 따로 표시하며, `Python OR HCX`는 HCX 오류 시 Python 결과를 보존한다. `독립 HCX 문장 판정 응답률`은 전체 공급 문장 행 중 `success` 비율로 별도 집계한다. 현재 UI가 검토하는 `P+/H-`·`P-/H+` 표본의 지표는 **불일치 검토 표본 조건부 지표**이며 전체 기사 문장 성능이 아니다. 분모가 0인 정밀도·재현율은 0%로 표시하지 않고 `산출 불가`로 표시하며 TP·FP·FN·TN을 함께 공개한다. 불일치 유형의 건수 자체를 정확도라고 부르지 않는다.
- **구현 커밋:** 분류 `da7ea30`, `304881f`; 연구 저장 `a5abf8f`, `1d89a81`; 전체 비교 연결 `c4300da`, `bad15b4`, `108eca1`; 연구 UI·저장 `f7323eb`, `e55dbac`, `3877998`; CSV·검토·골든셋 `8526f61`, `12058a6`; 사람 검토 지표 `e39c5dd`.
- **검증:** `tests/test_experiment_analysis.py`, `tests/test_experiment_store.py`, `tests/test_experiment_lab.py`, `tests/test_experiment_research.py`, `tests/test_experiment_export.py`에서 분류 합계, 오류 우선순위, 저장 무결성, 중복 저장, 승인 제한, 지표 표본 제외와 fail-open을 고정한다.
- **남은 과제:** 축적된 사람 검토 표본에서 `Python OR HCX`가 Python 대비 재현율을 실제로 높이는지, 오탐과 비용 증가가 허용 가능한지 검증한 뒤에만 운영 하이브리드 변경을 결정한다.
- **상태:** Monitoring. 상호 보완 가설을 측정할 구조는 구현했지만, 충분한 사람 검토 사례와 운영 전환 근거는 아직 없다.

- **상태:** Monitoring. 확인된 데이터 손실·경합·캐시·내보내기 문제는 회귀 테스트와 함께 조치했으며, 아래 비차단 한계를 계속 관찰한다.
- **발견일 / 영역:** 2026-07-26 / 연구 저장 · 누적 조회 · CSV 내보내기 · UI · 보안
- **발견된 실패:** 초기 누적 조회는 최근 500개 실행만 가져오면서 전체처럼 표시해 조용한 절단 위험이 있었다. 같은 필터의 CSV도 매 Streamlit rerun마다 선제 생성되어 DB와 메모리 비용을 반복했다. 동일 `run_id`의 동시 저장은 `get` 후 `insert` 구조라 두 연결 사이에 경쟁 조건이 있었고, 같은 ID의 다른 payload를 명확히 거부하지 못했다.
- **캐시·상한 실패:** 준비한 CSV는 이후 새 실행 또는 사람 검토로 연구 DB가 바뀌어도 필터 문자열이 같으면 재사용될 수 있었다. UI 사전 집계만으로 행 상한을 판단하면 집계와 실제 cursor 순회 사이의 추가 행을 놓칠 수 있었고, 최종 CSV 바이트 상한은 없었다.
- **CSV·잠금 위생 실패:** 기존 스프레드시트 수식 방어는 `=`, `+`, `-`, `@`, TAB, CR 시작은 막았지만 LF 또는 선행 공백·제어문자 뒤의 수식은 막지 못했다. 골든셋 동시 쓰기의 advisory `.lock` 파일은 프로세스 종료 뒤 경로에 남을 수 있으므로 소스 관리 대상에서 명시적으로 제외해야 했다.
- **1차 조치 (`75097e5`):** `BEGIN IMMEDIATE` 기반 원자·멱등 실행 저장을 도입했다. 동일한 논리 실행의 동시 저장은 한 건만 생성하고 나머지는 정상 no-op으로 반환하며, 같은 `run_id`의 다른 불변 run·sentence payload는 거부한다. 연구 DB에서 과거 실행을 조회·검토·승격하고 다중 실행 CSV를 만들 수 있게 했으며 `data/goldenset/*.lock`을 `.gitignore`에 추가했다.
- **2차 조치 (`ce04cbc`):** 날짜·provider·model·prompt 필터를 SQL로 적용하고 실행 수·문장 수·다섯 유형을 정확 집계했다. 이력 목록은 50건 단위 페이지로 바꾸고, CSV는 사용자가 명시적으로 준비할 때만 생성한다. 실제 필터 결과가 50,000문장을 넘으면 `필터를 좁혀 주세요`로 거부하며 절단하지 않는다. LF와 선행 공백·제어문자 뒤의 수식도 apostrophe로 보호하고 현재 실행/과거 실행 피드백 키를 분리했다.
- **3차 조치 (`4b9404a`):** 연구 SQLite에 단일 `research_revision`을 안전하게 초기화·마이그레이션했다. 실제 run 생성 또는 실제 review 변경에서만 원자 증가하고, 정확한 멱등 no-op에서는 증가하지 않는다. 준비된 CSV 서명에 revision을 포함해 새 실행·검토 후 stale bytes를 폐기한다. CSV 생성 자체가 cursor의 `max_rows + 1`을 검사하므로 사전 집계와 무관하게 상한을 지키며, UTF-8 인코딩 바이트를 증분 합산해 50MiB를 넘으면 명확히 거부하고 부분 파일을 반환하지 않는다. 실제 payload의 행 수·바이트 수를 UI에 전달한다. 페이지 제어는 전체 페이지 번호 tuple 대신 `number_input`과 `page_count/current page` 메타데이터를 사용한다.
- **잠금 파일 해석:** `.lock` 경로가 남아 있다는 사실만으로 활성 잠금으로 판단하지 않는다. OS advisory lock이 실제 소유권을 결정하며, 이전 소유자의 메타데이터는 다음 정상 획득 때 교체된다. 잠금 경로는 Git에서 제외한다. 이 조치는 stale 파일의 저장소 오염을 막지만 네트워크 파일시스템 전체의 advisory lock 의미를 보장한다는 뜻은 아니다.
- **검증 증거:** `tests/test_experiment_research.py`의 실제 2-thread·독립 file-SQLite 저장 테스트, `tests/test_experiment_store.py`의 501개 실행 정확 집계·마지막 페이지 접근·revision·동시 동일 review no-op 테스트, `tests/test_experiment_export.py`의 501행 전체 export·실제 행 상한·oversized cell 바이트 상한·LF 수식 방어 테스트, `tests/test_experiment_history.py`의 revision 서명·상수 크기 페이지 helper 테스트, `tests/test_experiment_review.py`의 준비→검토/새 run 무효화 테스트, `tests/test_experiment_lab_ui.py`의 lazy export·50건 페이지·선택 과거 run 전달 wiring 테스트로 고정했다.
- **테스트 실행 기록:** `75097e5` 단계 관련 테스트 104건, `ce04cbc` 단계 관련 테스트 115건, `4b9404a` 최종 focused suite 74건이 각각 통과했고 `py_compile`과 `git diff --check`도 통과했다. 이 숫자는 서로 다른 시점의 겹치는 focused suite이므로 합산하지 않는다. 이 문서 후속 작업에서는 전체 프로젝트 suite를 새로 실행하지 않았으며, 전체 검증은 최종 통합 단계에서 별도로 수행한다. 기존 전체 suite 기준선 3건은 VLAB-011에 그대로 남아 있다.
- **남은 비차단 한계:**
  1. revision이 widget key에 포함되므로 사람 검토 뒤 revision이 바뀌면 과거 이력 페이지가 1페이지로 초기화된다. 데이터 정확성에는 영향이 없지만 검토 동선은 다시 맞춰야 한다.
  2. 동일 label·note라도 `reviewed_at`이 새 값이면 새 검토 이벤트로 보는 정책이므로 revision이 증가한다. 이는 감사 시점 보존을 우선한 의도된 정책이며, 향후 별도 review event 테이블 도입 시 재검토한다.
  3. 최종 CSV payload는 50MiB로 제한되지만 단일 매우 큰 셀을 UTF-8로 인코딩하는 순간의 peak allocation은 최종 파일 상한보다 커질 수 있다. 현재는 조용히 자르지 않고 명시적으로 거부하며, 필요하면 입력 셀 크기 사전 제한 또는 streaming response를 후속 설계한다.
  4. OFFSET 페이지는 정확한 총계와 bounded memory를 제공하지만 조회 도중 새 실행이 추가되면 인접 페이지의 항목이 이동할 수 있다. revision 변경이 캐시를 무효화하므로 데이터 혼합은 막지만, 장시간 탐색의 고정 snapshot UX는 후속 과제다.

  6. 좁은 정수 구간의 히스토그램이 역전된 범위나 실제 최대값 밖의 bin을 만들 수 있었다. 정수 domain에 맞춰 폭·개수를 다시 계산하고 최대 10개 bin으로 제한했다.

  8. 헤더만 있는 CSV는 분석되지 않았지만 아무 안내도 없었다. `row_count=0`을 명시적으로 경고하고 분석 경로에 진입하지 않도록 RED→GREEN 회귀 테스트로 수정했다.
  9. 선택한 1,000행 보고서의 `source_row_count`를 `원본 행`·`업로드 전체 행`으로 표시하면 5,000행 파일 전체를 분석한 것처럼 보였다. KPI를 `분석 행`으로 바꾸고 `전체 5,000행 중 1–1,000행 분석`처럼 업로드 모집단과 포함 구간을 별도 표시했다.
  10. 탐지 정규식에는 `개`가 있었지만 공용 parser 단위와 EDA 유형 매핑에는 없어 `판매량은 3개였다`가 수치 단위 후보에서 탈락했다. parser·query 단위와 EDA `count_rank`를 일치시키고 기존 `3인 가구` 복합명사 가드를 함께 회귀 검증했다.
  11. Python CSV 기본 필드 한도 131,072자 때문에 131,073자 정상 본문이 `_csv.Error`로 중단됐고 Streamlit은 이를 처리하지 못했다. 모듈 로드 시 일관된 5MiB 문자 상한을 한 번 설정하고, 상한 초과·malformed CSV를 위치 복원형 `EdaCsvReadError`로 변환해 자르지 않고 사용자 메시지로 중단한다.
