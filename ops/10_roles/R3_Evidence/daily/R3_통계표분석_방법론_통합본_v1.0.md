# Part I. 개념 — 왜 어려운가

## 1. 한 줄 정의

통계표 분석은 기사 수치와 KOSIS 숫자가 같은지 비교하는 작업이 **아니다.**

> 기사의 수치 Claim이 **어떤 통계 개념을 뜻하는지 구조화**하고,
> 그 Claim과 **의미가 같은** KOSIS 통계표 및 관측값 행을 찾아
> **재현 가능한 Evidence**로 만드는 과정이다.

전체 흐름:

```text
기사 원문
→ ① 수치 Claim 추출
→ ② KOSIS 대상 여부 분류
→ ③ Table Card 구성
→ ④ 후보 통계표 검색
→ ⑤ 강제 불일치 필터
→ ⑥ Top 3 제한 조회
→ ⑦ 통계표 내부 차원 분석
→ ⑧ 직접값 / 파생계산
→ ⑨ EvidenceRow 생성
→ 일치 / 불일치 / 판단불가
```

## 2. 문제의 크기

### 2.1 통계표 규모 [문서]

| 수치 | 의미 | 출처 |
|---|---|---|
| 288,663 | OpenAPI 제공 통계표 **전체** | KOSIS 공유서비스 소개 |
| 134,586 | **국내** 통계 기준 | KOSIS 이용안내 |
| 1,371 | 국가승인**통계** 건수 | 국가데이터처 |
| 4,602 | 회의 안건 문서(07-15) 기재. 우리 보존 xls 행 수와 일치 | **[미확인]** 기준 불명 — 백서는 이 수치를 다루지 않음 |

**모순이 아닌 이유**: 승인통계 1건(예: 농림어업조사)이 수십~수백 개 통계표로 **분해되어 수록**된다.
ClaFact의 매핑 문제는 정확히 이 지점에 있다 — **주장 하나를 28만 개 표 중 하나에 연결**해야 한다.

*288,663과 134,586의 정확한 기준 차이는 백서 §8.4(미확인사항 #7)에서도 미확인으로 남아 있다.
본 절의 수치는 모두 공식 문서 기재값이며, 백서 조사 시점에 kosis.kr 직접 접근이 차단되어 실호출 검증은 되지 않았다.*

### 2.2 [최중요] 전수 인덱싱은 원리상 불가능하다 [문서]

| 항목 | 수치 |
|---|---|
| 통계표 총수 | 288,663 |
| 표당 최소 메타 조회 | ×1 |
| 전수 인덱싱 필요 호출 | ≥ 288,663회 |
| 개발 계정 한도 | 1,000회 |
| **부족 배율** | **약 289배** |

운영 계정으로 증량해도 **분당 호출 제한**이 걸려 있어 전수 수집은 며칠 단위 작업이 된다.
6주 프로젝트에서 3주차 1주로는 불가능하다.

> **이것이 방법론 전체를 규정한다.**
> "모든 통계표를 미리 인덱싱해 두고 검색한다"는 계획은 **성립하지 않는다.**
> 남은 선택지는 두 가지뿐이며, 이는 코딩이 아니라 **착수 전 설계 결정**이다.

| 선택지 | 방식 | 호출 비용 | 커버리지 |
|---|---|---|---|
| (a) 도메인 제한 인덱싱 | 골든셋 도메인(고용·물가·농업 등)만 수집 | 수백~수천 회 | 제한적 — 범위 밖은 전부 판단불가 |
| (b) 경로 C (통합검색) | 인덱싱 없이 주장마다 KOSIS 검색엔진에 질의 | 주장당 1회 | **28만 표 전체** |

**권고**: 배타적이지 않다. (b)를 주 경로로 하되 (a)를 골든셋 도메인에 한해 병행한다.
경로 C가 실패해도 3주차 산출물이 남고, 어차피 둘의 비교가 EXP-001이다.

## 3. 직접 비교가 안 되는 다섯 가지 이유

### 3.1 기사 하나에 수치가 여러 개다

기사 하나에 출처와 의미가 다른 수치가 섞여 있다 — 출생아 수 / 전년 대비 증가율 / 혼인 건수 / 연령별 출산율 / 합계출산율.
기사 전체를 하나의 검색어로 쓰면 **어떤 수치를 검증하려는지 알 수 없다.**

### 3.2 모든 수치가 KOSIS 대상이 아니다

미국 고용 통계, 특정 기업 매출, 플랫폼 회원 수, 민간 연구기관 전망, 전문가 의견, 미래 예상치 —
이런 문장을 국내 KOSIS와 비교하면 **무관한 표를 억지로 선택하게 된다.**

### 3.3 이름이 비슷해도 의미가 다르다

"인구"가 들어간 통계표만 해도: 총인구 / 주민등록인구 / 경제활동인구 / 취업인구 / 농가인구 / 외국인 인구.
**단어가 겹친다는 이유만으로 같은 통계라고 판단할 수 없다.**

### 3.4 통계표마다 구조가 다르다

`C1`, `C2`, `C3`의 의미가 통계표마다 다르다.

```text
통계표 A          통계표 B          통계표 C
C1 = 지역         C1 = 연령         C1 = 농가 유형
C2 = 성별         C2 = 산업         C2 = 경지 규모
```

**표준이 없다.** 따라서 매핑 모듈은 통계표별로 분류/항목 메타를 **먼저 조회해 축 배치를 파악한 뒤** 질의를 구성해야 한다.

### 3.5 기사 원문의 85%가 잡음이었다 [확인]

전처리 전에는 광고·댓글·관련기사·푸터가 본문에 섞여 있었다.

```text
G001~G200 정제 결과
  원본  2,630,451자
  정제    396,337자  (15.1% 유지)
```

광고의 "97%", 푸터의 전화번호·등록번호가 **수치 주장으로 오탐**되는 것으로 **추정된다**(탐지 단계 재측정 필요).
따라서 **전처리는 매핑의 전제조건**이지 별개 작업이 아니다.

## 4. 핵심 해결책 — Retrieval과 Grounding 분리

이 분리가 방법론의 중심이다. **두 문제는 성격이 다르고, 따로 측정해야 한다.**

### 4.1 Retrieval — 맞는 통계표를 찾기

> 정답 통계표가 후보 Top 10 또는 Top 3 안에 들어왔는가?

이 단계에서는 통계표 **수치를 보지 않는다.** 메타데이터만으로 후보를 좁힌다.

사용 정보: 통계표명 · 통계명/조사명 · 작성기관 · KOSIS 분류경로 · 항목명 · 단위 · 수록기간 · 공표주기 · 분류축 · 지표 별칭

```text
Claim 1개 → 후보 Top 10 → 의미 필터 → 후보 Top 3
```

### 4.2 Grounding — 표 안에서 정확한 행 찾기

> 선택한 통계표의 어느 항목·기간·지역·모집단 행이 이 Claim의 Evidence인가?

`TBL_ID`를 찾으면 끝나는 게 아니다.

```text
정답 통계표 + 정답 항목 + 정답 기간 + 정답 지역
+ 정답 모집단 + 정답 단위 = 검증 가능한 EvidenceRow
```

> **검색 성능이 좋아도 잘못된 행에서 숫자를 가져오면 최종 판정은 실패한다.**
> 그래서 Hit@k만 올려서는 정확도가 오르지 않는다.

## 5. 표준 견본 — 과수 농가 고령화율 [확인]

클라비가 제시하고 우리가 실 API로 **재현에 성공한** 사례다. ClaFact 난이도의 기준 견본으로 삼는다.

```text
기사 주장 : "농가 고령화" — 과수 농가 10곳 중 6곳이 고령 (≈64.2%)
      ↓
KOSIS 현실 : "과수 농가 고령화율"이라는 항목은 존재하지 않는다
      ↓
필요 작업 :
  ① 통계표 식별      농림어업조사 (orgId=101)
  ② 축 배치 파악      영농형태 → objL / 연령 → ITM
  ③ 분류값 번역      "과수 농가" → "영농형태 : 과수"
  ④ 분모 조회        2024년 과수 농가 총계 = 166,558 가구
  ⑤ 분자 조회·합산    65세 이상 4개 구간 합계 = 106,877 가구
  ⑥ 파생 계산        106,877 ÷ 166,558 ≈ 64.2%
  ⑦ 판정             기사 수치와 일치
```

**이 한 건에 전 난이도가 들어 있다** — 항목 부재, 축 배치 비표준, 용어 번역, 다중 조회, 구간 합산, 파생 계산, 반올림.
골든셋의 "파생계산형" 난이도 태그는 이 사례를 기준으로 정의한다.

# Part II. 근거원 — KOSIS를 정확히 알기

> 근거원을 깊이 아는 것이 곧 시스템의 성능이다. 이것이 본 프로젝트의 성격이다.

## 6. 통계표의 해부학

### 6.1 통계표를 식별하는 좌표

통계표 하나는 `orgId` + `tblId` 조합으로 **유일하게 식별**된다.

| 요소 | 의미 | 예시 |
|---|---|---|
| `orgId` | 기관 ID | 101 = 국가데이터처(구 통계청), 116 = 국토교통부 |
| `tblId` | 통계표 ID | `DT_1B040A3`, `DT_MLTM_2086` (`DT_` 접두 관행) |

### 6.2 값 하나를 특정하는 5개 축

통계표는 표가 아니라 **다차원 큐브**다. 수치 하나를 꺼내려면 아래를 **전부** 지정해야 한다.

| 축 | 파라미터 | 의미 | 비고 |
|---|---|---|---|
| 분류 | `objL1`~`objL8` | 행 분류 코드 (최대 8단계) | `objL1` 필수. 실무상 5~8은 거의 안 쓰임 |
| 항목 | `itmId` | 항목 코드 | 필수 |
| 주기 | `prdSe` | 수록 주기 | Y(연) H(반기) Q(분기) M(월) D(일) IR(부정기) |
| 시점 | `startPrdDe`/`endPrdDe` 또는 `newEstPrdCnt` | 수록 시점 | 형식은 주기에 종속 |
| 값 | (응답) `DT` | 수치값 | — |

**응답 필드 전체**: `ORG_ID`, `TBL_ID`, `TBL_NM`, `C1`~`C8`(분류값 ID), `C1_OBJ_NM`~`C8_OBJ_NM`(분류 **축**의 이름), `C1_NM`~`C8_NM`(분류**값**의 이름), `ITM_ID`, `ITM_NM`, `UNIT_NM`, `PRD_SE`, `PRD_DE`, `DT`, `LST_CHN_DE`

### 6.3 시점 표기 규칙

| `prdSe` | 형식 | 예시 |
|---|---|---|
| Y (연) | YYYY | 2024 |
| H (반기) | YYYYHH (HH: 01,02) | 202401 |
| Q (분기) | YYYYQQ (QQ: 01~04) | 202403 |
| M (월) | YYYYMM | 202412 |
| D (일) | YYYYMMDD | 20241231 |

**주의**: `startPrdDe`/`endPrdDe`(시점 기준)와 `newEstPrdCnt`(최신 자료 기준)는 **택 1**이며,
아무 설정이 없으면 **최근 시점 1개만** 조회된다.
기사가 "지난해"라고만 쓴 경우 상대시점 해석을 거쳐 절대시점으로 변환한 뒤 명시적으로 지정해야 한다.

## 7. Open API 7종 [확인]

**정정 사항**: 기존 문서(01 제안서 §7.2, 04 데이터·API 명세서, 18 아이펠톤 제안서 §3.3)는 API를 **"4종"**으로 기술한다.
**실제로는 7종**이며 명칭도 일부 다르다. 해당 절을 갱신해야 한다.

| # | API | R3 용도 |
|---|---|---|
| 1 | 통계목록 (`vwCd` 기반) | 인덱스 코퍼스 구성. **트리 재귀 순회 필요** — 1회로 안 끝남 |
| 2 | 통계자료 | **판정 엔진의 입력.** 통계표 선택(URL 생성) 방식이 우리에게 적합 |
| 3 | 대용량 통계자료 | 자료 등록 후 조회만 가능 → 우리 용도에 부적합 |
| 4 | 통계설명(조사 설명자료) | **모집단 판정 + 별칭 사전 자동 시드** (§7.2) |
| 5 | 통계표설명 (하위 9종) | **축 배치 파악의 핵심** (§7.3) |
| 6 | **KOSIS 통합검색** | **경로 C·D의 기반** (§7.4) |
| 7 | 통계주요지표 | 자주 인용되는 대표 지표(실업률·물가상승률)의 지름길 |

### 7.1 공통 사항

| 항목 | 내용 |
|---|---|
| 통신 방식 | REST. **HTTPS만** (2026.02.05 HTTP 종료) |
| 응답 형태 | JSON, XML, SDMX, XLS |
| 인증 | `apiKey` 파라미터. **회원당 1개**, 1개 키로 전 서비스 |
| 신청 | 공유서비스 → 활용신청 탭 → 제출 시 **자동 승인** |

*인터넷의 옛 예제 코드는 대부분 `http://`다. 복사해 쓰면 즉시 실패한다.*

### 7.2 통계설명 API — 과소평가하고 있던 광맥

기존 문서는 이 API를 "모집단·정의 확인" 정도로만 적었다. 실제로는 **자산 A1·A2를 직접 살찌운다.**

| 필드 | 의미 | R3 활용 |
|---|---|---|
| `mainTermExpl` | 주요 용어 해설 | **별칭 사전(A1) 자동 시드** — 기사어↔통계어 번역의 공식 출처 |
| `examinObjrange` | 조사 대상 범위 | **모집단 불일치 판정의 직접 근거** |
| `dataUserNote` | 이용자 유의사항 | 한계 고지 설명의 소스 |
| `examinHistory` | 조사 연혁 | **시계열 단절 탐지** |
| `statsEnd` | 통계 종료 | **판단불가 근거** — 종료된 통계는 최신 주장 검증 불가 |
| `examinObjArea` | 조사 대상 지역 | 지역 한정 주장 검증 |
| `josaUnit` | 조사 단위 | 단위 혼동 판정 |
| `confmNo` / `confmDt` | 승인번호 / 승인일자 | "국가승인통계 제○○○호에 근거" 표기 |
| `statsPeriod` / `pubPeriod` / `examinTrgetPd` | 작성/공표 주기, 조사 대상 기간 | 시점 판정 |

> 별칭 사전을 손으로 채우고 있다면 **여기서 시드를 자동으로 뽑을 수 있다.**

### 7.3 통계표설명 — 하위 9종

기존 문서가 "메타정보"라 부르던 것. 정확한 명칭은 **통계표설명**이며 9개 서브서비스로 세분된다.

| # | 서브서비스 | 주요 응답 | R3 용도 |
|---|---|---|---|
| 1 | 통계표명칭 | `TBL_NM` | 인덱스 문서 |
| 2 | 기관명칭 | `ORG_NM` | 출처 표기 |
| 3 | 수록정보 | `PRD_SE`, `PRD_DE` | **어떤 시점이 실제로 있는지** — 시점 판정 전제 |
| 4 | **분류/항목** | `OBJ_ID`, `OBJ_NM`, `ITM_ID`, `ITM_NM`, **`UP_ITM_ID`** | **축 배치 파악 + 계층 구조** |
| 5 | 주석 | `CMMT_DC` | 정의 변경·특이사항 → 판단불가 근거 |
| 6 | 단위 | `UNIT_NM` | 단위 환산 판정의 기준값 |
| 7 | 출처 | `JOSA_NM`, `DEPT_NM` | 근거 표기 |
| 8 | 가중치 | `WGT_CO` | 지수 검증 시 (2차) |
| 9 | 자료갱신일 | `SEND_DE` | 기사 작성일 대조 — *단, `LST_CHN_DE`로 대체 가능 (§21)* |

**`UP_ITM_ID`(상위 항목 ID)가 핵심이다.** 항목이 **계층 구조**를 가진다는 뜻이다.

과수 농가 사례에서 "65세 이상 4개 구간"을 **수작업으로** 골라 합산했다. `UP_ITM_ID`를 따라가면:

- 구간 합산 대상을 **자동 도출** → 파생계산형 주장의 일반화
- 분모(전체) 항목을 자동 식별
- **이중계상 방지**

### 7.4 KOSIS 통합검색 — 매핑 문제의 판도를 바꾼 발견

| 구분 | 내용 |
|---|---|
| 요청 | `searchNm`(필수), `orgId`(선택), `sort`(RANK 정확도순 / DATE 최신순), `startCount`, `resultCount` |
| 응답 | `ORG_ID`, `ORG_NM`, `TBL_ID`, `TBL_NM`, `STAT_ID`, `STAT_NM`, `VW_CD`, `MT_ATITLE`, `FULL_PATH_ID`, `CONTENTS`, **`STRT_PRD_DE`**, **`END_PRD_DE`**, `TBL_VIEW_URL` |

우리는 "주장 → 통계표" 매핑을 위해 **직접 임베딩 인덱스를 구축**하는 계획을 세웠다.
그런데 KOSIS는 **자체 검색엔진을 API로 열어 두었다.** 28만 표에 대한 정확도 순위 검색을 무료로 제공한다.

**부가 이득**: `STRT_PRD_DE`/`END_PRD_DE`로 후보 단계에서 수록 기간을 바로 알 수 있다
→ 기사 시점을 포함하지 않는 통계표를 **조회 전에** 후보에서 제거. 호출 예산 절감에 직결된다.

**단, 검증 필요**: 통합검색은 자연어 문장이 아니라 **검색어**를 받는다.
Claim에서 좋은 검색어를 생성하는 **질의생성 품질이 경로 C의 성패를 가른다.** 이 자체가 실험 변수다.

## 8. 실측으로만 알 수 있었던 것 [확인]

공식 문서를 읽는 것과 API를 아는 것은 다른 일이다. 6개 항목 중 **4개는 공식 문서에 없다.**

| 항목 | 공식 문서 | 우리 실측 (2026-07-14) |
|---|---|---|
| 통계자료 필수 파라미터 | `objL1`, `itmId`, `prdSe` | **`objL1`~`8` 전부 + `newEstPrdCnt`** 없으면 `err21` |
| 분류값 형식 | 명시 없음 | **`"영농형태 : 과수"`** — 축 이름과 값이 한 문자열에 결합 |
| 연령 차원 위치 | 통계표별 상이 | **`ITM` 차원** (농림어업조사). `objL`에서 찾으면 영원히 못 찾음 |
| 비브라우저 접근 | 명시 없음 | **RST 차단** — curl, Python, curl_cffi 전부 실패 |
| HTTPS 필수 | 2026.02.05 종료 | HTTPS로 호출 중 — 일치 |
| 과수농가 2024 수치 | 클라비 제시값 | **실 API로 재현 성공** |

> **문서보다 실측을 따른다.** `HttpKosisClient`는 `objL1`~`8`을 전부 포함하도록 하드코딩되어 있다.

## 9. 운영 제약

### 9.1 호출 한도

| 제약 | 수치 | 영향 |
|---|---|---|
| 개발 계정 트래픽 | **1,000회** | 골든셋 200~300 주장 × (후보 3~5개 × 메타 조회 여러 건) → **평가 배치 1회로 소진 가능** |
| 운영 계정 | 활용사례 등록 시 증량 요청 | **즉시 신청 필요** |
| 1회 호출 최대 | 40,000건 | 단건 조회 위주라 여유 |
| 분당 호출 제한 | 2026.02.05 + 2026.07.09 공지 | **레이트 리미터 필수** — [미확인] 정확한 수치 |

**즉시 조치 3건**

1. **운영 계정 전환 신청** — 착수 후가 아니라 **지금**. 승인 대기가 일정 리스크가 되지 않도록
2. **캐시 계층 필수화** — 같은 `(orgId, tblId, 시점)`은 재호출하지 않는다. 평가 하네스는 반복 실행이 전제이므로 **캐시 없이는 돌릴수록 한도가 녹는다.** 성능 최적화가 아니라 생존 조건
3. **레이트 리미터 + 지수 백오프**

**운영 지침**: ① 로컬 개발은 **브라우저 브릿지 또는** 픽스처로 ② 실 API 대량 호출은 **클라우드에서** ③ 공식 공지 확인은 **크롬으로 직접**

## 14. 4단계 — 후보 통계표 검색

### 14.1 네 개 경로

| 경로 | 방식 | 상태 |
|---|---|---|
| **A** | 별칭 사전 + 키워드. 점수 = `∩ / √∪` | 구현 완료 — **기준선** |
| **B** | 임베딩 + 리랭커 (자체 인덱스) | **문자 n-gram TF-IDF 프록시.** HCX 임베딩 미구현 |
| **C** | KOSIS 통합검색 (`searchNm` + `sort=RANK`) | 코드 완성, **실검색 0회** — G1 게이트 |
| **D** | C로 후보 생성 → 리랭커 재정렬 (하이브리드) | RRF 융합 (k=60). **유력 후보** |

**EXP-001은 A/B/C/D 4파전이다.** (기존 A vs B 2파전에서 확장)

### 14.2 경로 A — 별칭 사전

```text
출생아  ↔ 출생자 ↔ 출생건수
취업자  ↔ 취업인구
소비자물가 ↔ 소비자물가지수 ↔ CPI
농가    ↔ 농가수 ↔ 농가 가구
통계청  ↔ 국가데이터처          ← §10
```

**별칭은 동일 개념인 경우만 연결한다.** `인구`와 `경제활동인구`는 관련어지만 같은 지표가 아니다.

**실측 교훈 (오탐 사례)**

| 잘못된 키워드 | 문제 | 교체 |
|---|---|---|
| `어가` | '들어가', '이어가기로'에 걸려 **62건 오탐** | `어업가구` |
| `고령` | '최고령 희생자'에 걸림 | `고령화`, `고령 인구` |

### 14.3 질의 생성 — 경로 C의 성패를 가르는 단계

```text
별칭 치환 → 수량 스팬 제거 → 조사 제거 → 노이즈 컷
```

**주의**: 수량 스팬을 **통째로** 제거해야 한다. 단위어만 지우면 `'1인 가구'`의 `'가구'`(핵심어)까지 죽는다.

**실측**: 긴 문장 질의는 실 KOSIS에서 `err30`으로 **30건 중 27건 실패**했다. 짧은 지표어만 결과를 반환한다.

### 14.4 리랭커 — 결정적 규칙 (LLM 아님, 추가 API 비용 0)

| 조건 | 가감점 |
|---|---:|
| 핵심어가 문장·표 메타 양쪽에 존재 | +2.5 |
| 국제기구 통계 (국내 주장에 부적합) | −5.0 |
| 국내 주제별 통계 | +2.0 |
| 지역 주장 ↔ 지역표 일치 / 불일치 | +2.0 / −3.0 |
| 월간 주장 ↔ 월별 표 일치 / 연도별 표 | +4.0 / −3.0 |
| 조사명 정합 | +1.5 |
| 수록기간 커버 / 미커버 | +1.0 / −4.0 |

각 행에 `_rerank_score`와 `_rerank_why`(근거 문자열)를 붙여 **감사 추적**이 가능하다.

**탄생 배경**: 2026-07-20 실측에서 '소비자물가' 질의 1위가 지역·연간표였고, 월간 주장에 필요한 월별 표는 7위였다.
그 결과 **오'불일치' 판정**이 났다.

**[결정필요] 현재 한계**: +2.5 가점 대상 핵심어가 `("청년", "출생아", "실업률")` **3개 하드코딩**이다.
물가·1인 가구·농가 등 나머지 축은 이 가점을 받지 못한다.

## 21. [1] 잠정치 vs 확정치 — 가장 위험한 함정

통계는 **잠정치로 먼저 공표되고 나중에 확정치로 갱신**된다.
국가 통계 작성 가이드라인은 "공표된 잠정치·확정치 간 불일치의 원인을 분석하여 관리"하도록 명시한다.
즉 **불일치는 예외가 아니라 정상 절차다.**

| 시나리오 | 순진한 시스템 | 옳은 판정 |
|---|---|---|
| 2025년 3월 기사가 잠정치 "7.2%" 인용 → 이후 확정치 "7.4%"로 갱신 → 2026년에 검증 | 불일치 — 기사가 틀렸다 | **일치** — 기사 작성 시점 기준으로 정확했음. 단 "이후 7.4%로 갱신됨"을 한계로 고지 |

### 21.1 [확인] vintage 미지원, 그러나 `LST_CHN_DE`가 있다

**① KOSIS API는 과거 공표값(vintage)을 제공하지 않는다.**
요청 변수 전체(`startPrdDe`/`endPrdDe`/`newEstPrdCnt`/`prdInterval`)는 모두 **수록시점**(그 값이 어느 기간에 관한 것인가)을 가리킬 뿐,
**공표 시점**(언제 발표된 값인가)을 지정하는 파라미터는 **존재하지 않는다.**

**② 그런데 응답에 `LST_CHN_DE`(최종수정일)가 온다.** 데이터 행과 함께 **무료로** 오므로 별도 호출이 필요 없다.

### 21.2 확정된 구현 (A2-0012)

| 조건 | 판정 |
|---|---|
| `LST_CHN_DE` ≤ 기사 작성일 | 기사가 본 값 = 지금 값 → **정상 판정** (일치/불일치) |
| `LST_CHN_DE` > 기사 작성일 | 기사 이후 수정됨 → **판단불가**<br>사유: "해당 통계는 기사 작성 이후 수정되었으므로(최종수정일 ○○○○-○○-○○) 기사 시점의 공표값을 본 시스템이 확인할 수 없습니다" |

> 이것이 **원칙 ①(근거가 없으면 판정하지 않는다)의 가장 정직한 적용 사례**이며,
> 동시에 우리 시스템의 **회피 능력을 보여주는 최고의 데모 시나리오**다.

**계획 대비 이득**: 애초 계획은 자료갱신일 API(`SEND_DE`)를 **별도 호출**하는 것이었으나,
`LST_CHN_DE`가 통계자료 응답에 포함되므로 **추가 호출 0회**다. 주장 1건당 1회를 아낀다.

**[미확인]**: `LST_CHN_DE`가 행 단위인지 표 단위인지는 실 응답으로 확인해야 한다.
표 단위라면 판정이 보수적(표의 어느 값이든 수정되면 전체가 판단불가)이 되지만, **보수적인 쪽이 안전**하므로 그대로 채택한다.

## 22. [2] 공표 후 정정 — 통계법 §27

통계작성기관의 장은 공표한 통계에 오류가 있으면 **지체 없이 수정하고 공표**해야 한다.
즉 **KOSIS의 값도 사후에 바뀔 수 있다.**

> **"KOSIS = 절대 진리"라는 전제는 틀렸다.**
> 시스템은 "**KOSIS 현재 공표값 기준으로 대조했다**"고 말해야지, "사실이다/거짓이다"라고 말하면 안 된다.

**표현 규칙 (강제)**: 설명 생성 프롬프트에 제약을 건다.

```text
금지 : "사실이다" / "거짓이다"
사용 : "공식 통계와 일치" / "공식 통계와 불일치"
```

## 23. [3] 기준연도 개편 — 지수 비교의 함정

지수 통계(소비자물가지수 등)는 통상 **5년마다 지수개편**을 한다.
소비자물가지수는 기준연도가 **2015 → 2020**으로 변경(2021.12 개편)되었고, 가중치 기준연도도 2017 → 2020으로 바뀌었다.
(현재 2020=100, 458개 품목)

| 함정 | 내용 |
|---|---|
| 지수값 직접 비교 불가 | 2015=100 기준과 2020=100 기준은 **같은 척도가 아니다** |
| 과거 기사의 지수 인용 | 2021년 이전 기사가 인용한 지수는 2015 기준일 수 있는데, 지금 조회하면 2020 기준 값이 나온다 |
| 품목 구성 변경 | 개편 시 대표품목이 바뀌므로 세부품목 지수는 연속성이 없을 수 있음 |

**A2-0013**: 지수 성격의 지표는 **기준연도가 일치하는지 확인한 뒤에만** 비교한다. 다르거나 확인 불가면 판단불가.

통계표명에 `(2020=100)` 형태로 기준연도가 표기되는 경우가 많으므로 **표명 파싱으로 추출 가능**하다.
(예: `품목별 소비자물가지수(품목성질별: 2020=100)`)

→ 골든셋 난이도 태그에 **"기준연도형" 추가.** 물가는 기사에 가장 자주 나오는 통계 중 하나이므로 실전 비중이 크다.

## 24. [4] 시계열 단절

조사 방법 변경·분류체계 개편 등으로 **과거와 현재를 이어 비교할 수 없는 구간**이 존재한다.

**탐지 수단**: 통계설명의 `examinHistory`(조사 연혁), 통계표설명의 주석 `CMMT_DC`

"증감형" 주장(전년 대비 ○% 증가)은 단절 구간을 건너뛰면 무의미해지므로, **증감 판정 전에 이 두 필드를 확인**하는 단계를 넣는다.

## 25. [5] 작성중지 통계

`MT_STOP_TITLE`(작성중지통계) 뷰와 `statsEnd`(통계 종료) 필드가 있다는 것은 **더 이상 작성되지 않는 통계가 다수 있다**는 뜻이다.

> **판단불가에도 품질 차이가 있다.**
> "모르겠다"가 아니라 "**이 통계는 ○○년 작성 중지되었기 때문에 확인할 수 없다**"가 훨씬 나은 회피다.
> 설명 품질 루브릭의 "한계 고지" 축에서 **2점**을 받는 형태다.

## 26. [6] 공표 시차

통계는 조사 대상 기간 이후 **일정 시차를 두고 공표**된다. 연간통계는 통상 다음 해에 나온다.

**함의**: 2025년 기사가 "올해 ○○"라고 쓸 때, **2025년 통계는 아직 존재하지 않을 수 있다.**
기사는 2024년 값을 "최신"으로 인용한 것이다.

> 상대시점 해석은 "올해" → 기사 작성 연도로 **단순 변환하면 안 되고**,
> 해당 통계표의 수록정보(`PRD_DE`)와 대조해 **실제 최신 시점**을 찾아야 한다.

과수 농가 사례에서도 2025년 기사가 2024년 통계를 인용했다 — **이것이 정상이다.**

# Part V. 평가

## 28. 골든셋의 역할

> 골든셋은 **전체 KOSIS 데이터와 비교하는 대상이 아니라, 검색·매핑 방법을 평가하는 정답지다.**

### 28.1 골든셋에 필요한 정답

```text
claim_id
정답 또는 수용 가능한 tbl_id 목록
정답 item / period / dimensions / unit
정답 official value
파생 계산식
Evidence URL
최종 상태
```

### 28.2 [결정필요] 복수 정답 문제

같은 수치를 여러 통계표가 포함할 수 있다 — 전국 월별 표 / 전국 연간 표 / 지역별 표의 전국 합계 / 특정 조사 결과표.

현재 `mapping_eval.jsonl`의 `gold_tbl_id`가 **단일 문자열**이라 정상 후보도 오답 처리된다.

**권장 방식**

```text
gold_tbl_ids:      [DT_A, DT_B]   ← 수용 가능한 복수 정답
preferred_tbl_id:  DT_A           ← 대표 정답
```

### 28.3 골든셋 오염 방지

LLM이나 분류기의 출력이 정답지에 들어가면 **평가 자체가 무의미해진다.**
골든셋의 정답은 사람이 원 통계표를 직접 확인해 기록한 것이어야 한다.

## 29. Retrieval 지표

| 지표 | 정의 | 읽는 법 |
|---|---|---|
| **Hit@1** | 1위 후보가 정답인가 | 자동화 가능성. 사람 개입 없이 끝나는 비율 |
| **Hit@3** | 상위 3개 안에 정답이 있는가 | 리랭커 개선 여지. 낮으면 검색 자체가 문제 |
| **Recall@10** | 상위 10개 안에 수용 가능한 정답이 하나 이상 있는가 | 후보 생성기의 상한 |
| **MRR** | 정답이 처음 나온 순위의 역수 평균 | 순위 품질의 종합 지표 |

**MRR 계산**

```text
정답이 1위 → 1/1 = 1.00
정답이 2위 → 1/2 = 0.50
정답이 3위 → 1/3 = 0.33
못 찾음    → 0
→ 전체 Claim에 대해 평균
```

**[주의] 절단형 MRR**: 저장소의 `exp001_ab.py`는 top-3 밖이면 0으로 처리하는 **k=3 절단형**이다.
표준 MRR과 다르므로 보고 시 반드시 명시한다.

**Hit@1 · Hit@3 · Recall@10의 관계**

```text
Hit@1 낮고 Hit@3 높다      → 리랭킹 문제. 후보는 찾았는데 순위가 밀림
Hit@3 낮고 Recall@10 높다  → 필터·리랭커 문제
Recall@10도 낮다           → 후보 생성기(질의·인덱스) 자체 문제
```

## 30. Grounding 지표

Retrieval과 **별도로 측정한다.** 표를 찾아도 행이 틀리면 판정이 실패한다.

- 정답 항목 선택 정확도
- 기간 정확도
- 지역 정확도
- 모집단 정확도
- 단위 정확도
- **EvidenceRow exact match** (모든 좌표가 일치)
- 공식값 정확도
- 파생계산 정확도

## 31. 안전성 지표

| 지표 | 의미 |
|---|---|
| 위험 오매핑 수 | 무관한 표를 Evidence로 채택한 건수 |
| 무관 표 채택 비율 | 위 / 전체 |
| **판단불가 처리 정확도** | Evidence가 없을 때 정직하게 회피했는가 |
| **`NO_EVIDENCE` vs `RETRIEVAL_FAILED` 구분 정확도** | 검색 실패를 데이터 부재로 위장하지 않았는가 |

> ClaFact 원칙 ②(정직한 회피)는 **측정 가능해야 원칙이다.**
> 안전성 지표가 없으면 "판단불가를 남발해서 오답률을 낮추는" 퇴행을 잡아낼 수 없다.

## 32. 지표를 공식화하는 조건

저장소 자체 원칙이 **"하네스에 없는 지표는 없는 지표"**다.

현재 Hit@k·MRR은 `scripts/exp001_ab.py` 안에 **인라인으로만** 있고,
`clafact/eval/metrics.py`와 `harness.py`에는 편입되지 않았다.

> **`run_eval.py` 한 줄로 매핑 점수가 나와야 공식 지표가 된다.**
> 그 전까지 매핑 성능은 프로젝트 공식 지표가 아니다.

## 36. LLM과 Python의 역할 분담

| LLM이 **보조**할 수 있는 것 | Python이 **결정**해야 하는 것 |
|---|---|
| 지표명 추출 | 후보 점수 계산 |
| 모집단 추정 | 기간 범위 검사 |
| 지역·기간 문맥 해석 | 단위 변환 |
| 통계표 설명 요약 | 파생값 계산 |
| 별칭 후보 생성 | 허용오차 적용 |
| 불확실 Claim의 검토 사유 설명 | Hit@k·MRR 계산 |
| | 최종 규칙 기반 Verdict |
| | 재현 가능한 로그 생성 |

> **LLM은 의미 해석을 보조하지만, 공식값·계산·최종 판정은 결정적 로직으로 수행한다.**
> 이것이 ClaFact 원칙 ①의 구현이다.
